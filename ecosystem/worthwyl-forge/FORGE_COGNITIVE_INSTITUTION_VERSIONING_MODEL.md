# Forge Cognitive Institution Versioning Model

## 1. Purpose

This document defines how the Forge Cognitive Institution evolves without mutating Forge 1.0, corrupting provenance, or promoting architectural claims beyond executable evidence.

## 2. Versioning Principles

- Institutional Forge evolves through explicit versions.
- A version is an architectural state, not merely a release label.
- No component is considered implemented solely because it appears in a specification.
- Every institutional version maintains lineage to its predecessor and to the master specification.
- The institutional constitution remains stable across ordinary feature versions; constitutional change requires a formal amendment.
- Institutional version changes do not rewrite or mutate Forge 1.0.

## 3. Version Sequence

### 0.1 — Master Specification

The 41-document institutional architecture is established as the master specification.

Status: ARCHITECTURALLY_DEFINED.

### 0.2 — Partial Implementation Evidence

Selected institutional components may receive executable implementations and verification evidence, including Decision Spine, initial governance engines, and early memory interfaces.

Status: promoted only component-by-component when evidence exists.

### 0.3 — Governance Engine Prototypes

Governance, temporal, challenge, accountability, and reconciliation prototypes may be implemented and tested.

Status: promoted only by evidence.

### 0.4 — Institutional Memory, Forensics, and Counterfactuals

Institutional Memory, Cognitive Forensics, Counterfactual Engine, and related lineage services may be implemented.

Status: promoted only by evidence.

### 1.0 — First Institutional Release

Forge Cognitive Institution 1.0 requires demonstrated governance, accountability, continuity, reconstructability, and integration contracts appropriate to its release scope.

No claim of full implementation is made until release evidence exists.

## 4. Component Status Vocabulary

Use only:
- ARCHITECTURALLY_DEFINED
- IMPLEMENTED
- VERIFIED
- INTEGRATED
- SUPERSEDED
- DEPRECATED

A component may not skip directly from ARCHITECTURALLY_DEFINED to VERIFIED.

## 5. Promotion Gate

For each component:
1. specification exists
2. executable implementation exists
3. contract exists
4. tests exist
5. integration evidence exists where integration is claimed
6. verification command or reproducible verification path exists
7. registry entry identifies the component and status
8. provenance points to the governing version

## 6. Supersession

Supersession is explicit. A superseded artifact remains available for historical reconstruction unless legally or operationally required to be removed. Removal is not equivalent to supersession.

Each supersession event records prior version, replacement version, reason, evidence, effective time, affected capabilities, and compatibility impact.

## 7. Constitutional Amendments

Constitutional amendments are separate governed artifacts.

An amendment requires proposal, rationale, evidence, affected components, challenge results, impact analysis, review status, effective version, and superseded constitutional version.

Forge cannot silently amend its constitution.

## 8. Release Integrity

Every institutional release identifies architecture version, constitution version, policy versions, component status map, integration contracts, known limitations, verification evidence, superseded artifacts, and provenance root.

## 9. Versioning Rule

Version the institution. Do not rewrite the history.
